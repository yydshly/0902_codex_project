# 使用场景、扩展路线与对我们的意义

## 1. 适用对象

### 个人创作者和一人公司

匹配度最高。仓库把选题、搜索、素材归档、视频转写、内容拆解、图片/视频生成、长文草稿和知识沉淀串成了近似完整的个人内容供应链。

直接价值：

- 降低跨平台收集和整理的机械成本；
- 把作者自己的分析框架和质量标准固化下来；
- 产物默认进入本地文件和 Obsidian，而不是只留在聊天记录；
- 通过 dry-run、manifest 和回读减少“Agent 说完成但实际没完成”。

### 研究、咨询和内容运营人员

研究家族的来源路由、候选结构、coverage 和矛盾处理具有较高参考价值。它适合把一次性搜索变成有范围和证据账本的研究过程。

限制：仓库不是完整商业研究平台，不提供集中资料库、团队引用管理、统一账号治理或稳定的所有数据源 SLA。

### 重度微信/企微个人用户

本地 vault 可以把本人有权访问的聊天、联系人、群聊、朋友圈和收藏转成可查询文件，用于关系复盘、客户跟进和内容素材沉淀。

限制：这是最高风险的数据域。真实使用前必须确认数据所有权、组织政策、平台条款、设备安全、明文快照保留和备份规则。

### AI 工具和 Agent 平台开发者

仓库提供了大量 Skill 设计模式：触发描述、分层路由、外部适配器、handoff、doctor、权限闸门、状态机、证据化完成和兼容入口退役。

对这一人群而言，最有价值的是架构案例，不是作者的具体账号和内容工作流。

## 2. 典型场景

### 场景 A：从选题到内容资产

1. 用 `yichen-web-research` 固定主题、日期、地区和受众。
2. `yichen-unified-search` 从网页和平台返回标准候选。
3. 人工或 Agent 核验一手来源。
4. 用户明确选择后，`yichen-content-archive` 下载文章或媒体。
5. 音视频交给 `yichen-asr` 和 `yichen-volc-asr`。
6. `yichen-video-content` 拆解结构和逐句话术。
7. 使用 `yichen-x-slicer` 生成社交图片/视频，或 X Article uploader 创建长文草稿。
8. `yichen-summary` 或 Agent Memory Vault 保存结论。

价值在于每一步都可以单独验收，前一步的结果不会自动授权下一步的高风险动作。

### 场景 B：私人收藏迁移和归档

1. 用户当轮明确授权一个平台和范围。
2. `yichen-bookmarks-export` 只导出 URL，不下载正文或媒体。
3. 校验链接格式和抽样可访问性。
4. 如果用户另行要求，再把链接文件交给 `yichen-content-archive`。

该流程适合大量私人收藏的可迁移备份，也体现了“私人读取授权不等于下载授权”。

### 场景 C：公众号知识库

1. 已知文章 URL 可直接批量下载。
2. 公众号历史通过用户自有后台凭据获取。
3. 分别统计群发批次、展开 URL 数和原创文章数。
4. 需要阅读量或评论时，再进入用户确认的增强凭据流程。
5. Markdown、JSON、HTML 和图片归入本地知识库。

主要风险是登录、代理证书、指标权限、转载权和上游工具稳定性。

### 场景 D：口播视频粗剪

1. 复制原片为工作副本。
2. 豆包 ASR 生成时间戳和 SRT。
3. Agent 标注 KEEP、DELETE、CHECK。
4. FFmpeg 分段拼接生成粗剪。
5. 对粗剪成片重新 ASR，检查重复、残句、硬切和长停顿。
6. 通过后进入剪映做视觉、字幕和听感精修。

这里将“语义剪辑判断”和“确定性媒体切割”分开，是可复用的多模态工作流模式。

### 场景 E：多模型代码审查

1. Codex 验证单一项目和只读 Tunnel。
2. ChatGPT Pro 通过只读 MCP 获取真实项目证据并给 PLAN。
3. Codex 校验 PLAN 后修改和测试。
4. ChatGPT 读取真实 diff 和验证报告并给 REVIEW。
5. 结果进入 DONE、一次修复或 BLOCKED。

优势是模型分工和权限清晰；限制是私有 Runtime 未分发，公开仓库不能独立复现完整闭环。

## 3. 不适用场景

### 无人值守的高风险自动化

平台写入、密钥捕获、私有数据、桌面 UI 和付费 API 都需要动态授权或人工处理。仓库没有统一事务和补偿机制，不适合长时间无人监督执行。

### 大规模爬取和数据采购

多个 Skill 明确限制条数、分页、并发和登录态，目标是个人工作流，不是大规模采集平台。它也不应被用于绕过验证码、登录墙、付费墙或平台风控。

### 强 SLA 企业系统

浏览器 DOM、非官方 GraphQL、用户 Chrome 会话和第三方 CLI 缺少稳定 SLA。仓库没有多租户、RBAC、集中审计、灾难恢复或统一监控。

### 未获授权的商业使用

上游许可证明确禁止未经书面许可的公司内部部署、客户交付、付费产品、课程打包和商业工具包。技术上可运行不代表法律上可使用。

## 4. 扩展方向

### P0：先把个人 Skill 变成可治理组件

#### 统一机器可读 manifest

为每个 Skill 增加统一字段：

```yaml
name: example
version: 1.0.0
inputs: []
outputs: []
capabilities: []
network_destinations: []
credentials: []
side_effects: []
approval_gates: []
cost_model: unknown
idempotency: none
verification_contract: example/v1
supported_platforms: []
```

当前大量关键边界只存在自然语言中，难以由宿主自动审计或组合。

#### 跨平台抽象

- 将 POSIX `0600` 与 Windows ACL 封装成统一私有文件 API；
- 使用 `pathlib`/URL 语义测试，避免在断言中硬编码 `/`；
- 将 Keychain、Credential Manager 和 Linux secret service 做成 credential provider；
- 建立 macOS、Windows、Linux CI 矩阵；
- 明确每个 Skill 的支持/实验/不支持平台。

#### 许可与供应链治理

- 获取商业授权或采用独立 clean-room 实现；
- 为所有外部 CLI 固定版本、hash 和来源；
- 生成全仓 SBOM，而不仅是单个 Windows reader；
- 自动检查第三方许可证、凭据形态、私有路径和二进制完整性。

### P1：形成真正的 Skill 平台

#### Durable workflow engine

把跨 Skill 流程表达成 DAG：

```text
plan → discover → verify → approve → archive → transcribe → synthesize
```

每个节点提供：输入 hash、幂等键、状态、重试策略、费用、产物、人工审批和补偿动作。这样可以避免依赖对话上下文记住跨阶段状态。

#### Adapter SDK

将搜索和内容平台后端抽象成稳定接口：

- `doctor()`
- `capabilities()`
- `plan(request)`
- `execute(request)`
- `normalize(raw)`
- `verify(result)`
- `redact(log)`

新平台只增加 adapter，不修改上层路由器和 handoff。

#### 统一观测

记录并展示：

- 每个 Skill 的调用数、成功率、人工介入率；
- 平台 DOM/API 兼容失败率；
- 单任务成本、token、API 配额和媒体时长；
- 失败阶段、恢复方式和重复提交拦截；
- 产物 hash、来源和验证状态；
- 账号/凭据只记录引用和权限，不记录值。

### P2：扩展业务能力

#### 内容知识图谱

在归档和 Memory Vault 之间增加实体、主题、人物、平台、观点和来源关系；支持事实版本、冲突、失效时间和引用回溯。

#### 多模态理解

补充 OCR、视觉场景切分、说话人分离、画面/字幕一致性、素材版权元数据和成片质量评分。

#### 多渠道发布草稿

沿用“只创建草稿、回读验证、不自动发布”的模式，扩展公众号、知乎、LinkedIn、博客 CMS 等；每个平台保持独立发布授权。

#### 团队协作

增加用户、项目、角色、审批、密钥代理、知识权限、审计和数据保留策略。个人 vault 与团队事实库必须分离。

## 5. 对我们的意义

### 不是照抄个人能力表

作者的微信、X、剪映和 Obsidian 工作流未必与我们一致。直接复制会继承平台耦合、账号假设、维护成本和许可限制。

### 应复制的方法

对我们最重要的五个方法是：

1. 从真实重复任务提炼 Skill，而不是先设想一个无所不能的 Agent。
2. 同时定义“能做什么”和“绝不能做什么”。
3. 把判断交给 Agent，把可确定步骤交给脚本。
4. 将授权按动作分层，并禁止授权自动传递。
5. 用结构化证据定义完成，而不是相信模型的完成声明。

### 可以形成的内部资产

在许可允许或独立实现的前提下，我们可以形成：

- 团队 Skill catalog：能力、owner、版本、依赖、风险和支持状态；
- 通用 Skill template：触发、输入、流程、边界、异常、验收；
- adapter SDK：搜索、文件、浏览器、数据库和 SaaS 的统一接口；
- evidence contract：候选、事实、产物、验证和 handoff；
- evaluation suite：离线 fixture、真实 E2E、平台兼容和安全回归；
- operation dashboard：成本、成功率、等待、人工介入和平台漂移。

## 6. 建议的落地顺序

如果目标是建设自己的能力库，建议按风险递增：

1. **只读、纯本地：** 对话总结、代码库分析、文档整理。
2. **公开数据读取：** 搜索候选和已知 URL 阅读，但不下载、不登录。
3. **本地产物写入：** 报告、索引、manifest、媒体衍生文件，默认不覆盖。
4. **账号态只读：** 私人收藏、后台数据，使用精确当轮授权和凭据代理。
5. **外部草稿写入：** 只保存草稿并回读，发布仍由人完成。
6. **高风险写操作：** 删除、发送、支付、部署和权限变更继续保留人工最终确认。

### 评价指标

不要只看“任务完成率”，还应持续记录：

- 正确触发率和误触发率；
- 计划与实际执行后端的一致性；
- 结果回读通过率；
- 重复提交/重复计费拦截率；
- 人工介入时间；
- 凭据或隐私泄露事件；
- 平台升级后的恢复时间；
- 每次成功交付的总成本。

## 7. 最终判断

Yichen Skills 的直接产品价值集中在个人内容和本地数字资产工作流；其更广泛的研究价值，是证明一个 Agent 能力库应该沉淀的不只是 prompt，还包括路由、权限、执行器、证据、失败语义和维护经验。

对我们的最佳策略是“学习协议设计，选择性验证，独立治理执行层”，而不是未经授权整包安装到团队环境。
